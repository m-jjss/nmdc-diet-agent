# 方太个性化膳食规划 Agent 技术方案文档

## 项目概述

本项目构建了一个面向个性化健康饮食场景的膳食规划 Agent。系统不直接依赖大模型自由生成菜品，而是以真实菜谱库为候选空间，通过 RAG 检索、健康约束过滤、营养评估和 LLM 解释生成，形成一套可追溯、可校验、可部署的推荐流程。

项目目标包括：

1. 根据用户健康档案提供个性化菜品推荐。
2. 支持单人单餐、多人聚餐、多约束组合等典型场景。
3. 支持多轮对话中的偏好补充、约束追加和推荐调整。
4. 提供完整 API、部署配置和演示材料，满足比赛提交和现场展示需要。

## 系统架构

```text
用户输入
  │
  ▼
Flask API
  │
  ├── 意图识别 (LLM + 关键词回退)
  ├── 多轮对话状态管理 (DialogManager)
  │
  ▼
多 Agent 编排层 (AgentOrchestrator)
  ├── 协调 Agent：意图 -> 专职 Agent 语义路由 + 上下文分发
  ├── 偏好·约束 Agent：提取并落库口味/排除食材等偏好与硬约束
  ├── 检索·推荐 Agent：RAG + ReAct 推荐、追加、换菜、方案否定（默认兜底）
  ├── 营养 Agent：查询指定菜品营养信息（规则，不依赖 LLM）
  ├── 菜谱详情 Agent：返回食材与做法（规则，不依赖 LLM）
  └── 简单交互 Agent：问候 / 确认 / 取消 / 模糊回复
  │
  ▼
Agent ReAct 循环
  ├── Function Calling (search_recipes / check_constraints / ask_user)
  ├── DeepSeek v4-flash (thinking mode disabled)
  └── 工具执行与结果汇总
  │
  ▼
RAG 检索层
  ├── FAISS 向量检索 (sentence-transformers / 确定性哈希回退)
  └── 关键词检索 (回退方案)
  │
  ▼
约束引擎
  ├── 过敏原过滤
  ├── 慢性病禁忌过滤
  ├── 特殊人群限制
  ├── 口味偏好匹配
  └── 营养均衡评估 (Mifflin-St Jeor)
  │
  ▼
结果验证器 (ResultVerifier)
  ├── 菜谱存在性校验 (防幻觉)
  ├── 过敏原交叉检查
  ├── 疾病约束验证
  └── 违规菜品自动移除
  │
  ▼
响应生成
  ├── LLM 推荐理由解释
  ├── 按人营养摄入概览
  ├── 分阶段性能耗时统计
  └── 约束过紧时 LLM 现场生成新菜谱（加分项）
```

## 模块划分

| 模块 | 关键文件 | 说明 |
|------|----------|------|
| API 服务 | `app.py` | 提供健康检查、推荐、搜索、档案、营养、对话、流式对话、性能统计等接口，内置多 Agent 编排 + Agent ReAct 循环 |
| 多 Agent 编排 | `orchestrator.py` | 协调体 + 专职 Agent 架构：角色注册、意图路由、上下文分发，零新依赖、复用现有模块 |
| 配置管理 | `config.py` | 管理 LLM 服务商(DeepSeek)、向量维度(512)、数据路径、生成参数 |
| LLM 客户端 | `llm_client.py` | 封装 DeepSeek API 调用，支持 Function Calling / Embedding / 流式输出 |
| RAG 检索 | `rag_retriever.py` | 构建 FAISS 索引，sentence-transformers 语义检索 + 确定性哈希回退 |
| 约束引擎 | `constraint_engine.py` | 根据健康档案过滤候选菜品，多人约束合并，Mifflin-St Jeor 营养评估 |
| 对话管理 | `dialog_enhancer.py` | LLM 意图识别、用户偏好提取、6 种交互类型多轮对话状态维护 |
| 结果校验 | `result_verifier.py` | 实时拦截幻觉菜品和约束违规，自动从推荐列表中移除 |
| 自动评分 | `eval.py` | 竞赛评测脚本，16 组自建场景 + 25 组对话用例，覆盖 4 个评分维度 |

## 数据设计

### 菜谱数据

菜谱数据来自比赛提供的约 2000 道菜谱。预处理后保存为 `recipes_parsed.json`，主要字段包括：

```json
{
  "name": "菜名",
  "ingredients": ["食材1", "食材2"],
  "steps": "烹饪步骤",
  "tags": ["清淡", "家常"],
  "allergens": ["过敏原"],
  "cooking_time": 15,
  "difficulty": "简单"
}
```

预处理重点包括编码转换、食材解析、标签提取、过敏原识别和烹饪时间提取。

### 用户健康档案

用户健康档案保存为 `user_profiles_standardized.json`，包含年龄、性别、身高体重、BMI、过敏原、特殊人群、健康需求、口味偏好和体检指标。系统可利用血压、空腹血糖、尿酸、总胆固醇等字段辅助识别饮食限制。

### 营养数据库

营养数据库保存为 `nutrition_database.json`，覆盖 185 种常见食材，包含热量、蛋白质、脂肪、碳水化合物、膳食纤维和部分营养标签。它用于推荐结果的营养估算和均衡度评估。

## 检索策略

系统采用关键词检索与语义检索结合的混合策略：

| 检索方式 | 优点 | 适用场景 |
|----------|------|----------|
| 关键词检索 | 对菜名、食材、标签命中更稳定 | “清蒸”“鸡胸肉”“低糖”等明确需求 |
| 语义检索 | 能理解自然语言表达 | “适合控糖的晚餐”“老人吃得清淡一点” |

融合排序采用语义得分与关键词得分加权的方式，使系统既能理解用户表达，又不会忽视具体食材和标签。

```text
用户查询
  ├── 关键词检索
  └── 语义检索
        │
        ▼
融合排序
        │
        ▼
约束过滤
        │
        ▼
Top-K 推荐结果
```

## RAG 工程实践

### 向量化方案

Embedding 采用双轨策略，两套方案输出相同维度（512 维），FAISS 索引无需按环境重建：

| 方案 | 模型 | 说明 |
|------|------|------|
| 语义模型（首选） | sentence-transformers `BAAI/bge-small-zh-v1.5` | 中文语义理解（512 维），针对中文语料优化，评测环境（A100 GPU）自动启用，获得最佳检索精度 |
| 确定性哈希（回退） | 字符 n-gram + MD5 哈希 | 无需额外依赖，同文同向量，保证本地/离线环境可用 |

启动时优先加载 sentence-transformers，导入失败或环境不支持时自动回退到哈希方案，运行日志会输出实际采用的方案。

### 索引构建与缓存

- 启动预热阶段对全部菜谱（菜名 + 描述 + 食材）向量化并构建 FAISS 索引（`IndexFlatL2`）
- 索引支持磁盘持久化（`idx/recipe_index.faiss` + 映射 JSON），重复启动时直接从磁盘加载，避免重建
- 文本向量结果按 MD5 缓存，相同文本不重复计算
- 检索结果支持查询级缓存（5 分钟 TTL），相同会话相同消息直接命中

### 混合排序

检索结果综合四类信号排序：

1. 语义相似度得分（FAISS L2 距离转换，占主要权重）
2. 关键词匹配得分（菜名/食材/标签命中）
3. 餐次与场景加权（正餐降权甜点零食、提权主菜，早餐提权粥饼类）
4. 交叉编码器精排（`BAAI/bge-reranker-base`）对 Top 候选二次重排，进一步提升相关性

排序后做多样性重排（候选池轮转 + 按菜名去重），避免连续推荐相同烹饪方式或重复菜品。

### 回退机制

| 场景 | 回退方案 |
|------|----------|
| sentence-transformers 不可用 | 确定性哈希向量 |
| FAISS 不可用/索引构建失败 | 关键词匹配检索（`_simple_search`） |
| 检索结果为空 | LLM 现场生成合规新菜谱（`generated` 标记，约束引擎复检） |

## 约束推理

约束分为硬约束和软约束。硬约束必须满足，软约束用于排序和解释。

| 类型 | 约束 | 示例 |
|------|------|------|
| 硬约束 | 过敏原 | 海鲜、花生、鸡蛋、牛奶 |
| 硬约束 | 慢性病禁忌 | 高血压控钠、糖尿病控糖、高尿酸控嘌呤 |
| 硬约束 | 特殊人群限制 | 孕妇避免酒精、生食和高风险食材 |
| 软约束 | 口味偏好 | 清淡、少辣、低脂 |
| 软约束 | 营养需求 | 高蛋白、补铁、膳食纤维 |

多人场景中，系统优先满足会影响安全性的共同硬约束，再根据偏好和营养目标优化推荐组合。当需求冲突无法同时满足时，应在交互层提示用户调整优先级。

## Agent 架构

系统采用 ReAct (Reasoning + Acting) 模式实现智能推荐决策：

1. LLM 接收用户消息和对话上下文
2. 通过 Function Calling 自主决定调用工具：
   - `search_recipes` — 搜索菜谱库
   - `check_constraints` — 检查用户约束
   - `ask_user` — 信息不足时向用户提问
3. 工具返回结果后 LLM 继续推理，决定下一步操作
4. 满足退出条件后生成最终推荐和自然语言解释

相比传统 keyword→search→filter 流水线，Agent 路径的优势：
- 语义理解替代关键词匹配
- 模糊需求自动追问（"请问几个人吃？"）
- 多人场景识别低盐低嘌呤等隐含约束
- 方案否定时理解用户真实意图（"太清淡了" → 推荐重口味菜品）

DeepSeek v4-flash 默认开启 thinking mode 返回 reasoning_content，系统在 `chat_with_tools` 中捕获并原样回传，确保多轮对话中 reasoning 不丢失。

### 约束过紧时的新菜谱生成（加分项）

当用户约束极紧、菜谱库检索结果为空或全部被安全校验拦截时，系统调用 LLM 现场生成一道完全符合约束的新菜谱：

1. 汇总用户过敏原、疾病禁忌、特殊人群限制和对话偏好
2. LLM 生成菜名、食材、做法和标签（JSON 格式，最多重试 2 次）
3. 生成结果经约束引擎复检，未通过则反馈违规原因重新生成
4. 通过后返回菜谱并标记 `generated: True`，回复中明确标注"建议菜谱（生成）"

该策略遵循赛题规则（库内无法满足时可生成新菜谱且不扣分、可加分），同时保持"以真实菜谱库为优先"的原则——仅在所有候选均不满足时才触发生成，避免滥用 LLM 自由创作导致幻觉风险。

## Embedding 策略

| 策略 | 条件 | 维度 |
|------|------|------|
| sentence-transformers (`BAAI/bge-small-zh-v1.5`) | A100 GPU / 本地预装 | 512 |
| 确定性字符 n-gram 哈希 | 模型不可用时的回退 | 512 |

两者保持相同向量维度，FAISS 索引无需重建。竞赛评测环境（A100 GPU）将自动启用 sentence-transformers 获得最佳语义检索精度。

## RAG 生成流程

1. 解析用户输入，识别推荐意图、偏好、过敏原和健康目标。
2. 从菜谱库中检索候选菜品。
3. 根据用户档案执行过敏、疾病和偏好过滤。
4. 对候选菜品估算营养信息和均衡度。
5. 将候选菜品、用户需求和约束信息注入 Prompt。
6. 调用 LLM 生成简短、可理解的推荐理由。
7. 返回菜品列表、营养信息、推荐理由和耗时统计。

Prompt 设计原则是限制模型只解释候选结果，不让模型脱离菜谱库自由编造菜名。

## 多轮对话

对话管理模块负责提取并保存用户在连续对话中表达的偏好，例如“不吃海鲜”“不要辣”“想控糖”。同一 `user_id` 的后续请求会复用已提取的偏好，直到用户传入 `reset: true` 或主动取消。

对话状态采用 **JSON 文件持久化**（`.dialog_store/`，按 `user_id` 落盘），跨请求、跨服务重启均可恢复上下文与已沉淀的饮食目标；`reset: true` 时清除对应会话。该方案免外部依赖，适合比赛演示与本地测试。

## 性能优化

| 优化项 | 说明 |
|--------|------|
| 组件预热 | 启动时加载 LLM 客户端、RAG 检索器和约束引擎 |
| FAISS 索引 | 使用向量索引加速语义检索 |
| 交叉编码器精排 | bge-reranker-base 二次重排提升 Top 候选相关性 |
| 缓存策略 | 缓存 Embedding、检索和对话相关结果 |
| 单例模式 | 避免核心组件在每次请求中重复初始化 |
| 线程限制 | 限制 embedding/rerank 推理线程数，防止高频评测下 OMP 线程耗尽崩溃 |
| 批量候选 | 检索阶段取 `top_k × 2` 候选，过滤后再返回结果，并在最终出口统一约束安全网复检 |

性能说明需要区分两类耗时：本地检索、过滤、营养计算通常为毫秒级；远程 LLM 生成受网络和模型服务影响，可能为秒级。

## 技术边界

当前版本适合比赛演示和原型验证，仍有继续提升空间。营养估算依赖食材数据库覆盖率，复杂菜品的真实营养值可能存在误差；进程内对话状态不适合生产级多实例部署；多用户复杂聚餐场景目前以约束合并和候选排序为主，后续可进一步加入组合优化算法。

## 总结

本方案把大语言模型放在解释和交互层，把推荐安全性建立在真实菜谱检索和规则约束之上。这样的设计既发挥了 LLM 的自然语言能力，也保留了工程系统在可控性、可验证性和可部署性上的优势。

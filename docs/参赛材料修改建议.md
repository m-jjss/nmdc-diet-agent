# 参赛材料修改建议说明

## 整体判断

这套材料的基础较完整，已经覆盖代码、数据、接口、部署和演示脚本，适合参赛提交。主要问题不在“有没有功能”，而在评审阅读时容易感到口径不稳：文档里有些接口路径与代码不一致，性能数据没有区分本地检索和远程 LLM，视频脚本偏流程说明，作品摘要也更像功能清单，缺少对比赛题目的回应。

本次优化以“不改变核心项目方向、不重构业务逻辑”为原则，重点修正文档一致性、启动配置和容易暴露的演示问题。

## 已修改内容

| 文件 | 修改重点 |
|------|----------|
| `作品信息摘要.md` | 重写作品概述、技术亮点、创新点和测试说明，让摘要更贴近评审视角 |
| `技术方案文档.md` | 强化系统架构、RAG 流程、约束推理、多轮对话和性能说明，补充实现边界 |
| `API接口文档.md` | 统一接口路径、请求参数、响应字段和示例，避免演示时路径错误 |
| `部署文档.md` | 修正健康检查地址，补充本地与 Docker 启动说明，删除不稳定表述 |
| `演示视频脚本.md` | 改成 3-5 分钟可直接拍摄的叙事脚本，修正 API 调用示例 |
| `requirements.txt` | 删除重复依赖 |
| `config.py` | 补充 `DEBUG` 默认值，避免 `Config.DEBUG` 报错 |
| `app.py` | 修正多轮对话状态保存方式，避免每次请求都丢失上下文 |
| `docker-compose.yml` | 修正健康检查路径，并避免依赖容器内未安装的 `curl` |

## 还建议继续完善

1. 把“25/25 通过”的测试结果整理成截图或表格，提交时比单纯文字更可信。
2. 演示视频里尽量展示真实接口返回，不要只放 PPT；评审更看重可运行性。
3. 如果比赛允许，建议补充 1-2 个典型用户画像：例如“高血压中年男性”“孕期女性”“多人聚餐含过敏约束”。
4. 性能数据要分开讲：本地检索接口是毫秒级，远程 LLM 生成是秒级，避免被质疑。
5. 代码层面后续可继续增强对话状态持久化，目前优化版是进程内保存，服务重启后仍会丢失。
